# 민원서식 파싱 개선을 위한 사례와 판단 기준

## 목적과 기여 범위

민원 신청서의 입력 항목을 정리하고 서식 개선안을 만드는 과정에서 확인한 사례를 공유한다. 문서를 읽는 기반은 kordoc을 활용하고, 실제 서식의 검토 경험과 정답 사례를 파싱 개선에 보태는 것이 목적이다. 별도 편집기나 파서를 kordoc에 이식하는 제안은 아니다.

첫 기여는 문서와 합성 사례 데이터다. 파서·필드 인식기·채우기의 기존 동작이나 공개 API를 바꾸지 않는다. 아래 내용은 현재 kordoc에서 재현한 버그 목록이 아니다. 실제 재현 결과를 얻기 전에는 실패 사례나 성능 개선으로 집계하지 않는다.

기여자는 행정 실무자로서 AI 코딩 도구로 서식 검토 도구를 만들고, 원본과 결과를 대조하며 항목 관계를 수정했다. 규칙 코드를 그대로 가져오는 대신, 문제가 되는 입력 조건·기대 결과·반례를 먼저 제공한다.

## 기존 기능과 구분할 부분

현재 [필드 인식기](../src/form/recognize.ts)에는 라벨과 값 인식, 옆 셀의 하위 라벨 판별, 열 머리 판별, 중첩 표 순회, 날짜 자리표시 판별, 필드 타입·필수 표시·빈값 추론이 있다. 따라서 이를 모두 신규 기능으로 제안하지 않는다.

[IR 타입](../src/types.ts)의 `IRTable`과 `IRCell`은 병합과 셀 내부 블록을 표현한다. `IRCell.blocks`가 있으면 `text`는 평탄화된 호환용 텍스트이므로 두 경로를 합쳐 같은 항목을 중복 수집하지 않아야 한다. 여러 평문 문단만 있는 셀은 `blocks` 없이 줄바꿈으로 합친 `text`만 제공될 수 있다.

관심 있는 추가 검토 지점은 다음과 같다.

- 신청인과 대리인처럼 같은 라벨이 반복될 때의 상위 경로와 원본 표 식별
- 한 셀 안의 여러 입력값과 안내문·기재 틀 사이의 경계
- 반복 명부의 열 구조와 고정 행 이름을 구별하는 표현
- 파싱 결과를 사람이 수정한 정답과 비교하는 방법
- 자동화에 필요한 정보가 없을 때 추정 대신 미확정으로 남기는 계약

## 처리 단계를 나누는 기준

| 단계 | 확인할 질문 | 담당할 문제 |
|---|---|---|
| 원문 보존 | 문자·선택 표시·번호·문단·중첩 표가 빠지거나 중복됐는가 | 포맷 파싱과 표 IR |
| 필드 인식 | 어느 부분이 이름·값·자리표시·안내인가 | 기존 필드 인식·채우기와 함께 검토 |
| 의미 구조화 | 어느 그룹 소속이며 반복 목록인가 | 선택적인 후처리 또는 별도 결과 표현 |
| 업무 규칙 | 필수 입력이나 법적 수집 근거가 확정됐는가 | 행정서식 검토 도구의 영역 |
| 재구성 | 다른 배치로 바꿔도 내용과 구조가 보존되는가 | 결과물 생성과 담당자 검토 |

예를 들어 성명과 성별의 글자가 모두 보존됐는데 관계만 잘못 묶였다면 문자 파싱 누락과 구별한다. 서명란을 발견하는 것과 전자서명 기능을 제공하는 것도 별개의 일이다.

## 우선 공유할 사례

아래는 기존 작업에서 나온 문제 유형을 일반화한 것이다. 실제 정부 서식 원본을 첨부한 재현 시험이 아니라, [합성 사례 데이터](examples/government-form-parsing-cases.json)와 함께 읽는 판단 기준이다. 경로 표기는 설명을 위한 것이며 현재 kordoc API의 출력 형식으로 주장하지 않는다.

### C01 병합 제목과 실제 입력 항목

입력 예: 두 행을 덮는 ‘신청인’ 셀 오른쪽에 ‘성명 | 빈칸’, ‘주소 | 빈칸’이 있다.

기대 관계는 `신청인 → 성명`, `신청인 → 주소`다. 오른쪽의 ‘성명’을 신청인의 값으로 채우지 않아야 한다. 여기에는 기존 하위 라벨 판별 기능을 먼저 적용해 볼 수 있다.

반례: `성명 | 홍길동 | 빈칸`에서 ‘홍길동’을 구조 제목으로 승격하지 않는다. 병합 여부 하나만으로 판단하지 않고 작성된 값과 빈 입력 자리를 구분한다.

### C02 한 셀 안 성명과 성별

입력 예: ‘①성명’이라는 이름과 이름 작성 공간, ‘(남ㆍ여)’가 같은 작성 칸에 있다.

기대 관계는 ‘①성명’과 ‘성별’이라는 두 입력 항목이다. 이 작업의 의미 구조에서는 두 항목을 같은 단계에 둔다. 성명에 자체 입력값이 있는데 그룹으로만 바꾸면 이름을 적는 자리가 사라진다.

성별이라는 명칭은 원문 ‘남ㆍ여’를 해석해 붙이는 이름이다. 원본 그대로의 라벨과 해석해 붙인 이름을 구분할 필요가 있다. 물리적인 원본 셀 하나와 의미 필드 둘의 연결도 유지해야 한다.

### C03 이름은 같지만 역할이 다른 연락처

입력 A: `현지 연락처 | 주소 작성 공간 + (전화: 빈칸)`.

기대 결과 A: 현지 연락처 자체는 주소를 적는 글 항목이고, 전화는 같은 단계의 별도 항목이다. ‘연락처’라는 단어만 보고 셀 전체를 전화번호로 확정하지 않는다.

입력 B: `연락처 | (전화번호: 빈칸) (휴대전화번호: 빈칸)`.

기대 결과 B: 연락처 자체에 별도 값이 없으므로 ‘연락처’를 묶음으로 두고 전화번호와 휴대전화번호를 그 아래에 둔다.

반례: 연락처라고 쓰여 있다는 이유만으로 두 입력을 같은 구조로 만들지 않는다.

### C04 반복 명부와 고정 행 행렬

입력 A: ‘관계·성명·생년월일·직업’ 네 열 아래에 빈 행이 여러 개 반복된다.

기대 결과 A: 목록 하나와 네 개의 열 항목, 원본 행 수를 구분해 보관한다. 행별 채우기 필드는 그대로 필요할 수 있다. 목록 스키마를 만든다는 이유로 기존 행별 채우기 계약을 없애지는 않는다.

입력 B: 첫 열이 1월부터 12월로 정해져 있고 오른쪽에 수량과 금액을 적는다.

기대 결과 B: 월은 고정된 행 이름이다. 빈 명부처럼 임의의 행 추가를 제안하지 않는다. 수량과 금액을 같은 종류로 취급할지는 기존 타입 계약과 별도로 논의한다.

### C05 항목 뒤 안내문과 선택지 뒤 안내문

입력 예: `끝지점` 다음 문단에 `※ 공간이 부족하면 별지를 첨부합니다.`가 있다.

기대 결과: 끝지점은 입력 항목, 뒤 문장은 그 항목의 안내다. 안내 때문에 항목 전체가 탈락하거나 다음 그룹의 안내로 이동하지 않아야 한다.

선택지 뒤에 안내문이 붙어 있는 경우에도 선택지는 유지한다. `※`가 있다는 이유만으로 필수값이라고 해석하는 문제는 안내 부착과 구별해 검토한다.

### C06 표가 바뀌어도 이어지는 신청 영역

기존 작업의 주민등록표 열람 또는 등ㆍ초본 교부 신청서에서는 신청 문구가 다음 표에 있어 그 앞의 신청내용이 누락되는 문제가 있었다. 검토한 예시 판본은 2024년 12월 20일 판본이며 현행본 여부를 뜻하지 않는다.

기대 결과: 최상위 첫 표의 끝을 신청 항목의 끝으로 단정하지 않는다. 이어지는 표의 구획과 문구를 함께 확인하되 원본 표 경계·순서는 보존한다.

반례: 다음 표가 동의서나 위임장일 수 있으므로 모든 후속 표를 본문으로 합치지 않는다. 파싱 단계의 표 합치기와 의미 단계의 영역 연결은 다르다.

### C07 자동 번호와 그림 선택 기호

기존 작업에서는 화면에 보이는 제출서류의 첫 ‘1.’이 HWP 문자 레코드에 없어 목록 번호를 놓치는 문제가 있었다. PDF에서는 선택 기호가 텍스트가 아닌 작은 사각형으로 표현될 수 있다.

기대 결과: 화면에 있는 표지를 문자만으로 판별할 수 없는 경우를 재현 사례로 수집한다. 임의로 번호나 체크 상태를 만들어 넣지 않고, 확인된 원본 표현과 해당 포맷의 파싱 경로를 함께 검토한다.

반례: 번호 없는 문단 목록에 ‘1.’을 일괄 추가하지 않는다. 작은 사각형이라고 모두 체크박스로 확정하지 않는다.

### C08 셀 안 표와 텍스트의 순서 및 중복

입력 예: 셀 안에서 안내 문단 → 내부 표 → 추가 문단이 이어진다.

기대 결과: 부모 셀과 내부 표의 관계 및 읽기 순서를 유지한다. 내부 표의 내용이 부모 `text`와 `blocks` 양쪽에 표현돼도 입력 항목을 두 번 만들지 않는다.

내부 표를 읽을 수 있다는 것과 다른 레이아웃으로 안전하게 재구성할 수 있다는 것은 다르다. 재구성이 불확실하면 원본을 유지하면서 구조를 검토한다.

### C09 배경색만으로 작성자를 확정하지 않기

기존 작업에서는 회색 칸을 공무원 작성란으로 보는 규칙에 예외가 필요했다. 회색 칸에 안내문만 있거나 구획 제목이 들어 있는 경우가 있기 때문이다.

기대 결과: 색은 보조 신호다. 문구와 셀 역할을 함께 보고, 확인할 정보가 없으면 작성자 구분을 미확정으로 둔다. 현재 `IRCell`의 공개 필드에는 배경색이나 모든 포맷 공통 폭·높이 정보가 없으므로, 기존 색·크기 규칙의 즉시 이식을 전제로 하지 않는다.

### C10 기재 틀과 추가 입력 선택지

입력 예: `동번호 ( )개, 층수 ( )개`, `[ ] 기타( )`, `년 월 일`.

기대 결과: 수량의 단위·빈자리, 선택지 안의 추가 입력 자리, 날짜 자리표시를 보존한다. ‘기타’를 선택하는 행위와 괄호 안에 내용을 적는 행위는 구별한다.

반례: 이미 채워진 문구, 사진 규격, 안내용 괄호까지 입력 자리로 만들지 않는다. 원문에 명시되지 않은 정규식·허용 범위·필수 여부를 자동 확정하지 않는다.

## 원본으로 돌아갈 수 있는 결과 표현

후처리 결과를 추가한다면 다음 정보를 구분해 담는 방안을 검토할 수 있다. 아래는 설계 제안이며 새 타입이나 API 구현은 이 PR에 포함하지 않는다.

| 정보 | 용도 | 설계할 점 |
|---|---|---|
| 원문 라벨과 해석 라벨 | 원문과 사람이 붙인 이름 구별 | ‘남ㆍ여 → 성별’처럼 새 이름이 필요한 경우 |
| 그룹 경로 | 신청인 성명과 대리인 성명 구분 | 같은 이름·같은 경로의 반복 인스턴스도 구별 |
| 입력 종류와 기재 틀 | 날짜·선택·수량·자유기재 구분 | 기존 FormFieldSchema와 호환성 유지 |
| 목록 정의와 행 인스턴스 | 목록 스키마와 채우기 자리의 구분 | 반복 열, 원본 행 수, 고정 행 이름 |
| 원본 참조 | 원문 표·셀·쪽으로 돌아가기 | 블록 경로, 표 식별자, 앵커 행·열·병합 |
| 판단 근거와 상태 | 어떤 규칙을 적용했는지 설명 | 규칙 ID와 확정·추정·검토 필요 구별 |
| 버전 | 재현과 비교 | 파서·규칙·원본 판본의 구분 |

표 식별자와 좌표는 모든 포맷에서 같은 수준으로 제공되지 않는다. 예를 들어 현재 셀 `bbox`는 일부 PDF·OCR 경로에만 있고 아래 원점 PDF pt다. 화면의 위 원점 좌표와 연결할 때 변환이 필요하다. 존재하지 않는 좌표를 0으로 채우지 않는다.

## 파싱 결과로 만들 수 있는 후속 산출물

아래는 2026년 11월 7일 정리한 활용 아이디어를 기여 관점에서 다시 분류한 것이다. 이 PR에서 구현하거나 kordoc 코어에 모두 넣자는 뜻이 아니다. 기존 별도 도구의 구현 근거가 있는 부분도 kordoc 연동은 별도 확인이 필요하다.

| 후보 | 필요한 정보와 산출물 | 기존 작업과 이 PR의 관계 |
|---|---|---|
| 01 개정 검토 대비표 | 원문·제안·근거·담당자 반영 여부 | 별도 도구에 HTML·HWPX 작성 코드 있음. 업무 활용 예 |
| 02 근거 추적 카드 | 규칙 → 원본 셀 → 판정 → 결정 → 결과 위치 | 규칙·근거 자료를 연결하는 추가 아이디어 |
| 03 전자서식 구현 명세서 | 항목 경로·종류·선택지·원본 참조에서 개발용 스키마 생성 | 일반 항목 JSON 내보내기와 구별. 미확인 제약은 미확인으로 유지 |
| 04 입력 시뮬레이터 | 항목 구조를 시험용 입력 화면으로 표시 | 설계 검증 아이디어. 실제 접수·저장 기능 아님 |
| 05 처리절차와 체크시트 | 원문 단계·주체·기간·서류 | 별도 도구에 처리절차 인식 코드 있음. 역할별 레인은 확장 아이디어 |

## 공유 자료와 검증 방식

기존 작업에는 약 300건의 공개 서식 표본, 항목 트리 검토 자료, 사람이 직접 고친 정답, 회귀 비교 스크립트가 있다. 이 PR에는 원본 묶음이나 기존 소스 코드를 포함하지 않고 합성 사례만 넣는다.

2026년 11월 10일 기존 작업 기록은 ‘맞음’으로 저장한 정답 57건의 비교 결과 유지, 직접 고친 목표 정답 33건 중 23건 일치다. 비교기는 잎 항목의 경로·이름·종류·단위·선택지·열 정보를 대조하며, 순서·중복 개수·안내·필수 여부·좌표 전체를 검사하지 않는다. 따라서 이 수치를 전체 서식 정확도나 kordoc 성능으로 해석하지 않는다.

후속 검증에서는 다음을 각각 측정하는 것이 좋겠다.

1. 문자·선택 표시·표지의 보존과 순서
2. 표·병합·중첩 관계와 중복 추출
3. 필드의 누락·추가·라벨과 값의 경계
4. 그룹 관계와 반복 목록의 열·행 표현
5. 원본 위치 연결의 성공·실패 및 잘못된 연결

‘기존에 맞던 결과 유지’와 ‘사람이 고친 목표 결과에 가까워짐’을 나눠 기록한다. 실제 파일을 시험할 때는 원본 판본, 포맷, 파서 커밋·버전, 옵션, 실행 결과와 기대 결과를 함께 보관한다.

## 후속 작업 제안

먼저 합성 사례 중 현재 kordoc이 이미 처리하는 것과 추가 검토가 필요한 것을 분류한다. 다음으로 제작자가 고른 실제 빈 서식 몇 건에서 재현 여부를 확인한다. 원본 파싱 문제면 해당 포맷 경로의 작은 회귀 사례로, 의미 관계 문제면 선택적인 후처리 계약으로 나누어 기여한다.

이 문서의 목적은 새 엔진의 채택을 요청하는 것이 아니라, 행정서식 검토 경험을 재현 가능한 사례로 바꾸어 문서 읽기 기반을 함께 개선하는 데 있다.
